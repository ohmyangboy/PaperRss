# 自动化测试与分级验证矩阵

## 决策准则

- **最小充分验证**：仓库提供了多层级验证能力，Agent 应根据实际改动性质、风险与上下文自主权衡并决定执行策略，避免机械式跑全套流程。
- **决策启发**：根据改动范围选择最小充分验证手段，避免默认无差别执行 **\`**./scripts/verify.sh --all**\`**；同一代码状态下复用已通过证据，交付时客观陈述实际验证了哪些项目与遗留边界**
- **证据复用**：同一代码状态下复用已通过的验证证据。
- **客观陈述**：交付时客观陈述实际验证了哪些项目与遗留边界（例如环境无法点击真实 UI 时如实声明）。

## 分级验证矩阵

### 1. Tier 1 (纯 Core / 数据层)

- **适用范围**：`PaperRss/Sources/Core/` 承担的模型、解析、持久化、网络、同步、AI 和纯策略逻辑变动。
- **可用执行**：
  - **\`**./scripts/verify.sh --core**\`**（覆盖全量 Swift 单元/集成测试及 **\`**--feature**\`** 子集；**\`**./scripts/verify.sh --core**\`**（覆盖全量 Swift 单元/集成测试及 **\`**--feature**\`** 子集；纯 Core / 数据变更必须至少执行 `./scripts/verify.sh --core`（覆盖全量 Swift 单元/集成测试；开发排障可用 `--filter <名称>`）。
  - **开发排障可用 **\`**--filter <名称>**\`**）。已执行 **\`**--core**\`** 则无需重复跑局部测试；纯数据与核心逻辑改动免拉起 GUI。**若改动影响用户可见投影或行为，还必须执行 `./scripts/verify.sh --feature`（严禁表述为“--feature 或 --core”）。
- **运行特征**：免拉起 GUI 进程。

### 2. Tier 2 (Web / 治理 / 脚本)

- **适用范围**：Web Reader、JS Bridge、官网以及自动化脚本与仓库治理逻辑。
- **可用执行**：**\`**./scripts/verify.sh --web**\`**（测试 Web Reader、JS Bridge 逻辑与交互策略，Node 环境执行，免拉起 GUI）

### 3. Tier 3 (App 视图 / 系统桥接 / 视觉交互)

- **适用范围**：凡涉及 `PaperRss/Sources/App/`（如 SwiftUI 布局、主题色彩、Toolbar、侧边栏、快捷键、系统 Dock 联动及 `ArticleReaderView` 容器桥接）。
- **可用执行**：
  - **\`**./scripts/verify.sh --build**\`**）。环境无法观测真实 UI 时，如实说明需要人工验收交互，不将进程拉起等同于交互正常。**macOS 宿主编译构建**。
  - **\`**./scripts/dev.sh --isolated**\`**（编译 Debug 宿主并启动隔离实例，避免干扰用户正常使用的实例；其编译成功即可作为宿主构建证据，无需额外执行**执行 `./scripts/dev.sh --isolated` 启动隔离的真实 macOS 进程并进行实际交互观察**（避免关闭用户正在验收的正式实例；其编译成功即无需额外执行 `./scripts/verify.sh --build`）。
